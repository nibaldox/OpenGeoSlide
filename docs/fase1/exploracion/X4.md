# X4 — Publicación, CI y empaquetado (Fase 1)

## 1. Resumen

- **El repositorio no tiene remoto Git** (`git remote -v` no imprime nada) y **no existe `.github/`**: no hay CI, ni release, ni Pages.
- **Los `Cargo.toml` no se pueden publicar en crates.io tal como están**: `cargo package -p ogs-cli` falla con *"all dependencies must have a version requirement specified when packaging. dependency `ogs-core` does not specify a version"*. Solo `ogs-core` empaqueta, y con el aviso *"manifest has no documentation, homepage or repository"*.
- **Los nombres están libres** (consultas de solo lectura, todas **HTTP 404**): PyPI `opengeoslide`; crates.io `opengeoslide`, `ogs-core`, `ogs-cli`; npm `opengeoslide` y `@opengeoslide/*`; GitHub usuario/org `opengeoslide`. Sí están ocupados `ogs` en PyPI (OpenGeoSys 6.5.9) y en crates.io (juegos octales).
- **El build web ya compila a WASM y a `dist/`** (300 814 B de `.wasm`, 277 KB de JS), pero **el `dist/index.html` usa rutas absolutas `/assets/…`**: en un proyecto de Pages bajo `https://<usuario>.github.io/opengeoslide/` los assets darían 404. Se verificó que `base: '/opengeoslide/'` en Vite reescribe correctamente `index.html`, el worker (`new Worker(new URL('/opengeoslide/assets/worker-….js', import.meta.url))`) y el glue wasm (`new URL('/opengeoslide/assets/ogs_wasm_bg-….wasm', …)`).
- **No hace falta COOP/COEP**: `ogs-wasm` no usa `SharedArrayBuffer` ni hilos (rayon está tras la feature `parallel`, que no se activa en wasm). GitHub Pages además no permite cabeceras personalizadas, así que un PWA con `SharedArrayBuffer` quedaría fuera de alcance en Pages.
- **El `.wasm` no necesita `.nojekyll`**: `application/wasm` está en la tabla MIME de GitHub Pages (derivada de `mime-db`), confirmado en `mime-db` (`application/wasm -> ['wasm']`).
- **Wheel Python**: el `pyproject.toml` de `ogs-py` ya es PEP 639 puro (`license = "Apache-2.0"` → `License-Expression: Apache-2.0`, `Metadata-Version: 2.4`), confirmado en el wheel real. Falta `license-files` (el `LICENSE` está en la raíz del repo, dos niveles arriba) y el wheel local quedó en `manylinux_2_35` porque se compiló en glibc 2.44.
- **Recomendación de escritorio: PWA, no Tauri.** El motor ya es WASM y el bundle web es de ~590 kB; Tauri añadiría un `src-tauri/`, tres pipelines de firma y ~3–15 MB de instalador por un beneficio que aquí no se necesita.
- **Panorama 2026**: `xslope` (Apache-2.0, v1.1.0, 52 ★, paper en *SoftwareX*), `cSlope` 0.1.0 (MIT, el oráculo), `OGR Slip2D` (AGPL-3.0-or-later, suite OpenGeoRock) y un plugin de QGIS. **El hueco libre es "motor verificable en el navegador, sin escritorio"**.

**Metadatos de Cargo.**

| Crate | `description` | `license` | `repository` | `homepage` | `readme` |
|---|---|---|---|---|---|
| `ogs-core` | ✅ "Motor de estabilidad de taludes 2D por equilibrio límite (OpenGeoSlide)" | ✅ `Apache-2.0` (heredado) | ❌ | ❌ | ❌ |

| `ogs-py` | ✅ "Wrapper Python de ogs-core (PyO3 + maturin): paquete opengeoslide" | ✅ | ❌ | ❌ | ❌ |

El `license` y la `version` vienen de `[workspace.package]` en el `Cargo.toml` raíz (`version = "0.1.0"`, `edition = "2024"`, `license = "Apache-2.0"`). **No hay `rust-version`** en ningún manifiesto, aunque la edición 2024 exige Rust ≥ 1.85 (local: `rustc 1.97.1`).

**Bloqueante verificado para crates.io.** Ejecutado con `--target-dir` en scratch (no ensucia el repo):

```
$ cargo package -p ogs-cli --allow-dirty --no-verify
error: failed to verify manifest at `crates/ogs-cli/Cargo.toml`
Caused by:
  all dependencies must have a version requirement specified when packaging.
  dependency `ogs-core` does not specify a version
```

Idéntico error en `ogs-py` y `ogs-wasm`. `ogs-core` sí empaqueta, con el aviso `warning: manifest has no documentation, homepage or repository` (`cargo publish --dry-run -p ogs-core` → *"warning: aborting upload due to dry run"*). Causa raíz: las dependencias de ruta son `ogs-core = { path = "../ogs-core" }` sin `version`. Al publicar, Cargo elimina el `path` y necesita la versión de crates.io.

**Metadatos de `crates/ogs-py/pyproject.toml`.** `name = "opengeoslide"`, `dynamic = ["version"]`, `description = "Motor de estabilidad de taludes 2D por equilibrio límite (OpenGeoSlide)"`, `readme = "README.md"`, `license = "Apache-2.0"`, `requires-python = ">=3.11"`.

Verificado en el wheel real (`scratch/ogs-py-dist-prod/opengeoslide-0.1.0-cp311-abi3-manylinux_2_35_x86_64.whl`, `Generator: maturin (1.16.0)`): `Metadata-Version: 2.4`, `Name: opengeoslide`, `Version: 0.1.0`, `License-Expression: Apache-2.0`, `Requires-Python: >=3.11`, `Tag: cp311-abi3-manylinux_2_35_x86_64`.

Es decir, el `license = "Apache-2.0"` **ya se materializa como `License-Expression`** (PEP 639, soportado por maturin desde 1.9.0). Pero:

- **Falta `license-files`.** El wheel **no contiene ningún archivo LICENSE** (`has LICENSE in zip: NONE`) y el `METADATA` **no tiene ninguna línea `License-File`**. El `LICENSE` (Apache-2.0) está en la raíz del repo, dos niveles por encima del `pyproject.toml`; PEP 639 exige rutas relativas al `pyproject.toml`, y no se puede apuntar a `../../LICENSE`. Solución: **copiar `LICENSE` y `NOTICE` a `crates/ogs-py/`** o mover el `pyproject.toml` a la raíz.
- **El wheel local es `manylinux_2_35`**, no `manylinux2014`. Medido con `objdump -T`: el binario exige `GLIBC_2.35` como versión máxima. Se compiló sobre glibc 2.44 (CachyOS). PyPI acepta `manylinux_2_35` (PEP 600 acepta `manylinux_[0-9]+_[0-9]+_`), pero ese wheel **no instala en CentOS 7 / RHEL 8 / Ubuntu 20.04**. Para publicación hay que compilar dentro del contenedor `manylinux2014` (glibc 2.17), que es lo que hace `PyO3/maturin-action` por defecto.
- **`readme = "README.md"`** resuelve a `crates/ogs-py/README.md` ✅ (existe). Pero su enlace `../../README.md` **queda roto en PyPI** (fuera del paquete sdist).
- **No hay `classifiers` de licencia.** Correcto bajo PEP 639 (los `License ::` clásicos están deprecados); no añadir `License :: OSI Approved :: Apache Software License` mientras se mantenga el `License-Expression`.
- **El `pyproject.toml` no declara `authors`, `keywords` ni `classifiers` de dominio** (geotecnia). Es unafalta de metadatos, no un bloqueante.

**Scripts de build existentes.**

- `apps/web/scripts/build-wasm.sh`: `cargo build -p ogs-wasm --target wasm32-unknown-unknown --release` y luego `wasm-bindgen --target web --out-dir apps/web/src/wasm`. **No es parametrizable** (no acepta `--out-dir` ni `--target`), y usa `wasm-bindgen` del `PATH`, por lo que en CI hay que fijar la versión.
- `bench/run_all.sh`: 7 pasos (binario nativo, nativo paralelo con `--target-dir` aparte, wasm para web, wasm para Node, `pnpm install --frozen-lockfile && pnpm build`, Chrome headless, `bench/report.mjs` con gate de FS). Es un script de spike local: **usa `pnpm install` en vivo, no `--frozen-lockfile` en todos los pasos, y levanta un servidor Chrome en el puerto 5181**. No sirve como job de CI tal cual.
- `apps/web/package.json`: `"name": "@opengeoslide/web"`, `"private": true`, scripts `dev`/`build`/`preview`/`test`/`typecheck`. **Falta el campo `packageManager`** (pnpm 11.8.0 local), que es lo que fija la versión de pnpm en CI.
- `apps/web/pnpm-workspace.yaml` contiene `minimumReleaseAgeExclude: ['@types/react@19.3.1']`, o sea que la política de "edad mínima de publicación" **está activa por defecto** en pnpm 11 y solo se exime un paquete. En CI eso puede hacer fallar `pnpm install --frozen-lockfile` si una dependencia acaba de publicarse.
- `apps/web/.gitignore` excluye `src/wasm/` y `dist/`. Verificado con `git check-ignore -v`: el `.wasm` **nunca está versionado**. CI debe construirlo siempre.

**Sizes medidos** (`apps/web/dist/`, build local con Vite 8.3.8): `assets/index-*.js` 277 430 B; `assets/ogs_wasm_bg-*.wasm` 300 814 B (gzip 115 270); `assets/worker-*.js` 9 093 B; `assets/ogs_wasm-*.js` (glue) 3 493 B; `assets/index-*.css` 3 429 B; `index.html` 538 B. **Total `dist/` ≈ 595 kB.**

**El punto crítico de Pages**: `dist/index.html` (build actual, sin `base`) contiene `<script type="module" crossorigin src="/assets/index-C7HYRO8M.js">`. **Ruta absoluta**. En `https://<usuario>.github.io/opengeoslide/` el navegador pediría `/assets/index-….js` en el dominio raíz → 404.

**Verificación empírica del arreglo.** Se copió `apps/web` a scratch (`f1x-X4/webbase`), se añadió `base: '/opengeoslide/'` al `vite.config.ts` y se compiló (`vite build --outDir dist-base`, 162 ms): `index.html` 0,56 kB; `ogs_wasm-5HFzUY5z.js` 3,50 kB; `worker-COTu82qd.js` 9,09 kB; `ogs_wasm_bg-D3FwbFkn.wasm` 300,81 kB (gzip 115,27); `index-BzrRmiIH.js` 245,82 kB (gzip 77,79). Y las tres referencias quedan con el prefijo correcto:

```
index.html:  <script type="module" crossorigin src="/opengeoslide/assets/index-BzrRmiIH.js">
worker:      new Worker(new URL(`/opengeoslide/assets/worker-COTu82qd.js`, ``+import.meta.url),{type:`module`})
wasm glue:   e=new URL(`/opengeoslide/assets/ogs_wasm_bg-D3FwbFkn.wasm`, ``+import.meta.url)
```

El glue de wasm-bindgen además tiene el *fallback* documentado en el propio código generado: si `WebAssembly.instantiateStreaming` falla por MIME incorrecto, avisa por consola y cae a `WebAssembly.instantiate` (más lento, pero funciona). El glue usa `new URL(..., import.meta.url)` relativo al módulo, así que **el `.wasm` se resuelve correctamente bajo cualquier subruta sin tocar el glue**.

**Sobre MIME de `.wasm` en Pages.** GitHub Pages deriva su tabla MIME de `mime-db`. Consulta de solo lectura a `https://raw.githubusercontent.com/jshttp/mime-db/master/db.json` → `application/wasm -> ['wasm']` presente. El histórico `orgs/community#22863` (2018) lo denunciaba, pero la discusión de 2025 (`lefticus/cons_expr#18`) confirma que **hoy Pages sí sirve `application/wasm`**. No hace falta `_headers` (eso es Netlify/Cloudflare) ni `.nojekyll` (solo para directorios con `_`).

**Sobre COOP/COEP.** No hace falta, y además **no se podría**: GitHub Pages no permite cabeceras de respuesta personalizadas (discusión `orgs/community#13309`, sin fecha estimada; documentado en varios `DEPLOYMENT.md` de proyectos reales). El único camino sería un *service worker* que inyecte las cabeceras. **Innecesario aquí**: `ogs-wasm` no usa `SharedArrayBuffer` ni `Atomics`; rayon está tras la feature `parallel`, que solo se activa en nativo (`crates/ogs-core/src/search.rs`, `#[cfg(feature = "parallel")]`). El paralelismo en wasm queda fuera.

Notas de diseño:

- **Fijar `wasm-bindgen-cli` a la versión exacta del crate.** `crates/ogs-wasm/Cargo.toml` fija `wasm-bindgen = "=0.2.130"` y el `Cargo.lock` confirma `wasm-bindgen 0.2.130`. Un desajuste entre el CLI y el crate produce un *panic* de "schema version mismatch" en tiempo de ejecución. El script `build-wasm.sh` **usa el `wasm-bindgen` del `PATH`**, así que hay que instalarlo antes y verificar `wasm-bindgen --version` == 0.2.130. Alternativa más rápida que `cargo install` (que compila el CLI): `taiki-e/install-action@v2` con `tool: wasm-bindgen-cli@0.2.130` (binario precompilado).
- **El oráculo no necesita caché de repositorio.** `cslope==0.1.0` se instala desde PyPI con wheel precompilado. Lo que sí conviene cachear es el **venv de uv** (`astral-sh/setup-uv@v6` con `enable-cache: true`), no el clon de GitHub. **Tres requisitos de Pages que hay que resolver:**

1. **`base` de Vite.** Obligatorio si el repo no es `<usuario>.github.io`. La app vive en `https://<usuario>.github.io/opengeoslide/`, así que `base` debe ser `'/opengeoslide/'`. **Verificado empíricamente** (§2.1): con ese `base`, el `index.html`, el `new Worker(new URL(...))` y el `new URL(..._bg.wasm, import.meta.url)` del glue quedan los tres con el prefijo correcto. El `base` debe ser **configurable por variable de entorno** (`base: process.env.VITE_BASE ?? '/'`) para no atarlo al subruta: con dominio propio (`https://geoslide.org/`) el `base` sería `/` y con `base` fijo el sitio se rompería.
2. **MIME de `.wasm`.** `application/wasm` está en la tabla de Pages (`mime-db`: `application/wasm -> ['wasm']`). **No hace falta `.nojekyll`** (no hay directorios con `_` en `dist/`). Si aun así se quiere `.nojekyll` por costumbre, `actions/upload-pages-artifact@v3` **excluye los archivos ocultos por defecto** (`include-hidden-files: false`), así que habría que pasarlo a `true` explícitamente o el archivo se perdería en silencio. Mejor no añadirlo.
3. **COOP/COEP: no aplica.** El motor no usa `SharedArrayBuffer`. Y Pages no permite cabeceras personalizadas, así que la decisión es doblemente forzada. Si en el futuro el motor activase hilos en wasm, habría que migrar el hosting a Netlify/Cloudflare (que sí soportan `_headers`) o usar el truco del *service worker* `coi-serviceworker`.

**`wheels.yml`** — wheels abi3 con `PyO3/maturin-action`:

```yaml
name: wheels
on: { push: { tags: ['v*'] }, workflow_dispatch: }
permissions: { contents: read, id-token: write }   # ← id-token: requerido por Trusted Publishing
jobs:
  wheels:
    strategy:
      fail-fast: false
      matrix:
        include:
          - { os: ubuntu-latest, target: x86_64-unknown-linux-gnu, manylinux: 2014 }
          - { os: macos-latest,  target: aarch64-apple-darwin }
          - { os: macos-latest,  target: x86_64-apple-darwin }
          - { os: windows-latest, target: x86_64-pc-windows-msvc }
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
        with: { workspaces: 'crates/ogs-py -> target' }
      - uses: actions/setup-python@v5
        with: { python-version: '3.13' }
      - uses: PyO3/maturin-action@v1
        with:
          command: build
          args: --release --locked --compatibility pypi -i python3.13
          target: ${{ matrix.target }}
          manylinux: ${{ matrix.manylinux }}
          sccache: true
      - uses: actions/upload-artifact@v4
        with: { name: wheels-${{ matrix.target }}, path: target/wheels/*.whl }
  publish:
    needs: wheels
    environment: pypi
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with: { path: wheels, pattern: wheels-*, merge-multiple: true }
      - uses: pypa/gh-action-pypi-publish@release/v1
```

**Recetas a fijar:**

- **`--compatibility pypi`**: maturin ≥ 1.9 lo añade y bloquea la construcción de wheels con etiquetas que PyPI no acepta. Es una red de seguridad gratuita.
- **`manylinux: 2014`** explícito (glibc 2.17). Es el motivo por el que el wheel local (`manylinux_2_35`, requirement real `GLIBC_2.35`) **no sirve para publicar**: hay que compilar dentro del contenedor, no en el host. Con `manylinux: 2014` el requirement baja a 2.17 y el wheel sirve en CentOS 7, RHEL 8 y Ubuntu 20.04.
- **`abi3-py311`**: el crate ya usa `pyo3` con `features = ["extension-module", "abi3-py311"]`, así que **un solo wheel `cp311-abi3` por plataforma** cubre CPython ≥ 3.11 (3.11, 3.12, 3.13, 3.14). No hay matriz de versiones de Python. El `-i python3.13` solo fija el intérprete de construcción, no el ABI.
- **El `LICENSE` no está en `crates/ogs-py/`.** Hay que copiarlo (o mover el `pyproject.toml`) antes de publicar, si se quiere `License-File` en el wheel.
- **Trusted Publishing (OIDC)**: el job `publish` necesita `permissions: id-token: write` y `environment: pypi`. En PyPI, en *Manage → Publishing → GitHub Actions*, hay que registrar: propietario del repo, nombre del repo, **nombre del fichero de workflow** (p. ej. `wheels.yml`) y opcionalmente el environment `pypi`. Con environment se puede exigir aprobación manual antes de publicar, que es lo recomendable. Según la documentación de PyPI, el token resultante expira a los 15 minutos y sustituye a los tokens API de larga vida. El `id-token` solo se concede si el job está en un workflow del repositorio y el environment está configurado.

**`release.yml`** — crates.io (opcional) + GitHub Release:

- Es **bloqueante hoy** por la dependencia de ruta sin versión (§2.1). Arreglo mínimo:

  ```toml
  # crates/ogs-cli/Cargo.toml
  ogs-core = { version = "0.1.0", path = "../ogs-core" }
  ```

  y lo mismo en `ogs-py` y `ogs-wasm`. Con eso, `cargo package` funciona y el `path` se elimina al publicar.
- Añadir `repository`, `homepage`, `documentation` y `readme` en `[workspace.package]` y heredarlos con `repository.workspace = true` etc. Cargo lo pide para discoverability (la documentación de publicación lo lista como recomendados) y elimina el warning verificado.
- **Orden de publicación** (crates.io es inmutable): primero `ogs-core`, esperar a que crates.io indexe (~minutos), después `ogs-cli`. Publicar `ogs-cli` antes de que exista `ogs-core` deja el crate ininstalable.
- Token: `cargo login` con `CARGO_REGISTRY_TOKEN` desde un secret. crates.io **no tiene Trusted Publishing**; exige token. Alternativa moderna y sin secretos en el repo: `rust-lang/crates-io-auth-action` o `release-plz` con OIDC (verificar disponibilidad actual antes de depender de ella).
- **Límite de 10 MB por `.crate`** en crates.io: `ogs-core` empaqueta con `cargo package --list` → 21 ficheros, todos `.rs` + manifest. **Muy por debajo.** Sin riesgo.
- Recomiendo **`--dry-run` en CI** antes de publicar: `cargo publish --dry-run --locked`.

**Ficheros de soporte que faltan** (ninguno es bloqueante, pero mejoran la confianza):

- `CHANGELOG.md` (Keep a Changelog) — la documentación de publicación de crates.io lo recomienda por versión.
- `CITATION.cff` — la competencia (`xslope`) lo trae, con DOI de Zenodo. Es la puerta de entrada a la visibilidad académica.
- `CODE_OF_CONDUCT.md` y `SECURITY.md` — GitHub los pide en la plantilla de repositorio.
- `rust-toolchain.toml` — fija la versión de Rust en CI y en local (hoy depende de lo que haya instalado).

### 2.5 Escritorio: PWA frente a Tauri

| Criterio | PWA (instalable en el navegador) | Tauri v2 |
|---|---|---|
| Tamaño del artefacto | **`dist/` ≈ 595 kB** (medido) + caché del navegador | instalador de 3–15 MB (mínima ~600 KB; app real con React 5–15 MB) + WebView del SO |
| Dependencia extra | ninguna: reutiliza el WASM y la web que ya existen | **Nuevo crate `src-tauri/`**, config, plugins, un `Cargo.toml` más, otro toolchain (WebView2 en Windows, WKWebView en macOS, WebKitGTK en Linux) |
| Firma / cadena de confianza | **Ninguna**: HTTPS + Service Worker. Sin binario firmado que lestear ni que reemitir | Firma de código por SO (Authenticode en Windows, notarización en macOS), gestionada por `tauri-action` y el *updater* |
| Publicación | `actions/deploy-pages` — un `upload-pages-artifact` y listo | 3 plataformas × varios formatos (`.msi`, NSIS, `.dmg`, `.AppImage`, `.deb`, `.rpm`) + `tauri-action` + *updater* con `TAURI_SIGNING_PRIVATE_KEY` |
| Requisitos del sistema | navegador moderno; sin instalación | WebView2 (Windows), WebKitGTK + `libwebkit2gtk-4.1-dev` (Linux), Xcode (macOS) |
| Superficie de ataque | superficie del navegador | **un backend Rust nativo adicional** en el mismo proceso: `allowlist` de comandos IPC, permisos de filesystem, plugin de shell |
| Esfuerzo estimado | **bajo**: manifest + Service Worker + iconos (~1 día) | medio-alto: crate nuevo, bridging de IPC, firma, 3 pipelines de empaquetado y de firma, *updater* (semanas) |
| Limitación real | sin acceso al sistema de archivos: **el usuario no puede "abrir un `.ogs.json`" nativo** (hoy la web ya lo resuelve con `<input type=file>`) y el guardado es por descarga | acceso completo al filesystem |

**Recomendación: PWA en la Fase 1; Tauri solo si aparece un requisito de escritorio que lo justifique.**

Razones concretas:

1. **El valor de OpenGeoSlide no es el escritorio.** El activo diferencial es un motor **verificable** (38/38 checks publicados, 20/20 + 20/20 frente a cSlope) y **abierto** en el navegador. Una app de escritorio rompe la "una sola URL, sin instalación" que hace que la verificación sea pública y auditable.
2. **El coste marginal de Tauri es alto y el beneficio, bajo.** Un `src-tauri/` con su `Cargo.toml`, su bridging de IPC, tres cadenas de firma y tres pipelines de empaquetado es un **segundo producto** que mantener, con una superficie de seguridad nueva (el IPC nativo). Todo eso para obtener acceso al filesystem, que hoy la web resuelve con `<input type=file>` y una descarga.
3. **El wasm ya es el motor.** `ogs-wasm` existe y funciona; Tauri podría evitar el wasm embebido (el motor en Rust nativo), pero eso **duplicaría la ruta de cálculo** y obligaría a mantener dos backends que deben dar el mismo FS bit a bit. El repo ya tiene una regla de determinismo (el paralelismo de rayon no altera el orden de resultados) que eso multiplicaría.
4. **Firmas.** Una PWA no necesita firma de código: HTTPS + Service Worker. Tauri sí, y en macOS la notarización exige *Apple Developer ID*; en Windows, un certificado de firma de código (EV u OV) cuesta entre 100 y 400 USD/año. Es un coste recurrente que no se puede decidir por la vía técnica.
5. **Offline.** Es el argumento más fuerte a favor de la PWA: un Service Worker con *precache* del `index.html`, el JS, el CSS, el glue y el `.wasm` (300 kB) da una app offline completa por ~595 kB de tráfico, una sola vez. Con Tauri, el "offline" es gratis pero se paga con el instalador.

**Conclusión operativa**: Fase 1 → PWA instalable (`manifest.webmanifest` + Service Worker con precache del shell y del `.wasm`, iconos PNG 192/512, `display: standalone`). Dejar Tauri **documentado y sin hacer** (§3.4), para retomarlo si aparece el requisito de "abrir y guardar archivos en una carpeta de trabajo del usuario" o "instalar sin conexión en una máquina sin navegador".

Entra por la puerta de la interoperabilidad SIG.
5. **openslope** (PyPI, 0.0.1, 2026-10-14) — *early placeholder release*. No es competencia todavía, pero **ocupa el nombre más cercano**: si OpenGeoSlide quiere un alias de un solo término en PyPI, `openslope` ya no está disponible.

Ninguno de los tres cuerpos del panorama reúne las tres cosas: `xslope` es Apache-2.0 pero es escritorio+Python y su verificación es publicada en un *paper* revisado por pares; `OGR Slip2D` es AGPL; `cSlope` es MIT pero es motor sin editor gráfico y sin informe PDF.

8. **Hacia dónde va el mercado en 2026**: la convergencia es **LEM + FEM de seepage + probabilidad + sismos + Eurocode 7 + MCP para agentes**. `OGR Slip2D` publica un servidor MCP; `xslope` publica un *paper* revisado por pares. Un motor libre que solo haga LEM circular queda por detrás en cuanto a amplitud de funciones.
9. **Implicación estratégica para la Fase 1**: no competir en el número de métodos ni en seepage FEM (años-persona), sino en (a) **transparencia de la verificación** (checks publicados + oráculo), (b) **cero instalación** (navegador + `pip install`), (c) **interoperabilidad de formato abierto** (`.ogs.json` + DXF + CSV + informe PDF reproducible), y (d) **un informe PDF con la trazabilidad completa**: versión del motor, casos de verificación usados y advertencias.
10. **Ventana temporal**: `xslope` publica releases cada 2–4 días (1.0.5 → 1.1.0 entre el 2026-10-22 y el 2026-11-25) y `OGR Slip2D` está en pre-release activo. El público de la **Fase 1** (editor web + DXF/CSV + PDF) no está servido por ninguno de los dos. La prioridad es **publicar temprano y publicar bien**: un motor con informe PDF reproducible y verificación publicada es defendible; uno con una UI bonita, no.

### 3.2 Parámetros del esquema de CI

No hay schema que inventar aquí: lo que cambia son **archivos de workflow**. Los parámetros concretos que deben quedar fijados:

| Parámetro | Valor | Por qué |

### 3.3 Secuencia de publicación propuesta

```
Fase 1-A (sin red):
  1. Metadatos (Cargo.toml raíz + crates) y `license-files`.
  2. `.github/workflows/ci.yml` (fmt, clippy, tests, aceptación, web, pytest).
  3. Fijar pnpm con `packageManager` y `wasm-bindgen-cli` con `taiki-e/install-action`.

  4. Crear el repo `github.com/<owner>/opengeoslide` (usuario u organización `opengeoslide`
     están libres: HTTP 404 en /users/opengeoslide y 0 resultados en la búsqueda de repos).

  6. Activar Pages con *Source: GitHub Actions*; añadir `pages.yml`.
  7. Publicar `opengeoslide` en PyPI (proyecto vacío + Trusted Publisher apuntando a
```

**Ventana de riesgo por nombre**: los nombres están libres hoy, pero los registros son *first-come-first-serve*. Un `pip install opengeoslide` o un `cargo add ogs-core` por parte de un tercero bloquea la publicación. **Prioridad: publicar `opengeoslide` (PyPI) y `ogs-core` (crates.io) en cuanto haya CI verde**, aunque la versión sea `0.1.0` y el contenido sea el de la Fase 0. En PyPI, el proyecto y el Trusted Publisher deben crearse **antes** de la primera release pública.

### 3.4 Escritorio: la recomendación

**Fase 1 → PWA.** Manifest + Service Worker con precache del shell y del `.wasm` (≈ 595 kB), instalable desde el navegador, sin firma y sin instaladores. **Tauri → documentado y aplazado** a un requisito explícito (acceso nativo a archivos o instalación sin red).
